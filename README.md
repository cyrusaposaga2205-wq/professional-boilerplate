# Reflection Questions — Email Verification & Password Reset

## 1. Why is email verification important for security? What problems does it prevent?
Email verification confirms that the person registering an account actually owns and controls the email address they entered. Without it, anyone could sign up using someone else's email address, create fake or spam accounts in bulk, or lock a real user out of registering with their own email later. It also ensures that critical security notifications—like password reset links—are only delivered to a legitimate, reachable inbox owned by the account holder.

## 2. Explain the "always return success" pattern in forgot password. Why is it a security best practice?
In the "always return success" pattern, `POST /api/auth/forgot-password` returns a `200 OK` response with a generic message such as *"If an account with that email exists, a reset link has been sent"* regardless of whether the email exists in the `users` table. This prevents an attacker from probing the endpoint to discover which email addresses are registered in the system, removing a common reconnaissance vector used before credential stuffing or targeted phishing attacks.

## 3. What's the difference between a verification token and a reset token? Why do they have different expiration times?
A verification token (`verificationToken`) is generated during registration to confirm email ownership before activating login access, whereas a reset token (`resetPasswordToken`) is generated on demand when an existing user requests a password change. Verification tokens typically have a longer expiration window (such as 24 hours) because users may not check their inbox immediately after signing up and the account cannot log in until verified anyway. Reset tokens have a much shorter expiration window (such as 1 hour) because they grant direct authority to overwrite an active account's password, so minimizing their lifetime limits the window of exposure if an email inbox or link is compromised.

## 4. Why do we use `crypto.randomBytes(32)` instead of `Math.random()` or `Date.now()` for token generation?
`crypto.randomBytes(32)` uses the operating system's cryptographically secure pseudorandom number generator (CSPRNG) to produce 256 bits (64 hex characters) of high-entropy, unpredictable data. In contrast, `Math.random()` uses a deterministic algorithm seeded predictably, and `Date.now()` simply reflects the current timestamp—both of which would allow an attacker to guess or brute-force valid verification or reset tokens.

## 5. What happens if a user never verifies their email? How does your system handle this?
If a user never verifies their email, their record stays in the `users` table with `isVerified = false` (`0`), and `AuthService.login` blocks any login attempt with a `401 Unauthorized` error prompting them to check their inbox. If their initial verification token expires before they click it, they can request a fresh token via the resend-verification flow, and in a production environment, unverified accounts past a retention threshold could also be periodically purged by a scheduled cleanup job.

## 6. Explain why tokens are cleared after use. What security risk does this prevent?
Once a verification or password reset token is used, its column (`verificationToken` or `resetPasswordToken`) and corresponding expiry field are set back to `null` in MySQL. Clearing tokens enforces single-use behavior and prevents replay attacks—where someone with access to browser history, server logs, or an old email could reuse the same link later to re-verify an account or reset the password again after the user has already secured it.

## 7. What is email enumeration and how does your implementation prevent it?
Email enumeration occurs when an API reveals whether a specific email address is registered through differing HTTP status codes, error messages, or response times (for example, returning `404 User not found` on forgot-password). Our implementation prevents this on `POST /api/auth/forgot-password` by returning the exact same `200 OK` status and generic message whether the email exists in the database or not, only sending an email internally when a matching user record is found.

## 8. If you had to implement two-factor authentication (2FA) on top of this system, how would you approach it?
I would extend the `User` entity with fields such as `twoFactorEnabled` (boolean) and `twoFactorSecret` (encrypted TOTP secret, or hashed one-time codes for email/SMS OTP) along with backup recovery codes. After `AuthService.login` validates the email, password, and `isVerified` status, if `twoFactorEnabled` is `true`, it would return a short-lived temporary challenge token instead of the full access JWT. The client would then submit the 6-digit TOTP or OTP code alongside that challenge token to a `POST /api/auth/verify-2fa` endpoint, which validates the code and issues the final session JWT.

## 9. What are the trade-offs between using Ethereal (test service) vs. SendGrid (production service)?
Ethereal is free, requires zero domain verification, and captures outgoing SMTP messages in a web preview inbox so developers can test email flows safely without spamming real users—however, it never delivers messages to actual email providers. SendGrid delivers real emails at scale with analytics, bounce/complaint webhooks, and high inbox deliverability, but it requires API key management, sender domain authentication, usage monitoring, and paid tiers once free limits are exceeded.

## 10. How would you handle a situation where a user's email provider marks your emails as spam?
First, I would configure proper domain authentication records—specifically **SPF**, **DKIM**, and **DMARC**—on the sending domain so receiving mail servers can verify that our emails are legitimate and not spoofed. Second, I would use a reputable transactional email provider with dedicated/clean sending IPs, keep transactional templates clean with matching plain-text and HTML versions, avoid spam-trigger phrasing or URL shorteners, and provide a resend-verification endpoint plus clear UI guidance asking users to check their spam folder and whitelist our sender address.
